# Deterministic scenario playback

The six fixtures are normal, reducedLoading, risingTemp, combinedThermalMechanical, confirmedDemoStop and telemetryLoss. All scenario observations have source `demo`, a scenarioTag, a seeded device identity and deterministic sample IDs. Scenario readings are never published to the live bridge. No App controls, ESP32 settings, legacy alarm logs or localStorage keys are written.

The engine owns a shared clock with a fixed illustrative epoch (2026-01-01 UTC). Every simulated second produces a fixture frame. Time scale changes playback speed, not the values at a given simulated timestamp: rising temperature is exactly 0.4 °C/min and combined mechanical vibration rises by 0.4 ADC/s (24 ADC/min). Seeded normal vibration is indexed by simulated sample time, independent of callback batching. The runtime limits large browser scheduling gaps to one playback second per callback.

The selected scenario store's clock governs freshness, historical windows, trends, persistence, forecast horizons and accounting. The drone subscribes to that same clock without applying a second time multiplier. Scenario pause freezes everything on that clock. Hidden drone viewports freeze flight while scenario collection/accounting continue; no hidden-time flight catch-up occurs. Live ESP32 ingest continues independently and is not displayed in the scenario analysis.

Start/source selection and reset establish a fresh demo accounting session and restore illustrative production inputs. Scenario-owned production inputs are locked; what-if forecast controls remain separate. Only confirmedDemoStop emits an explicit confirmed stop, from second 60 through second 120. Temperature ramps keep speed at 2 m/s and running state unconfirmed by proximity. telemetryLoss omits observations during the same interval, yielding stale channels and unknown accounting gaps rather than confirmed downtime.

The combined scenario reaches warning levels at about 30 simulated seconds, produces compatible rising vibration/temperature evidence, then a NODE 01 recommendation and waypoint suggestion. Drone dispatch remains an explicit button action. An arrival snapshot is committed after the declared ten-second simulated inspection, tagged SIMULATION and described as linked sensor evidence.

Returning to the live bridge clears both incompatible scenario windows and old live analysis windows. Modules warm up again from new live observations; hardware accounting totals are retained separately and no demo tonnes are copied into them. The default App speed remains demo, so actual hardware throughput still requires calibrated hardware speed. Reset also clears drone findings and forecast sample boundaries, allowing identical seeded replay after rewinding the simulation clock.
